Defender status

Firewall & ASR coverage

🔗

Group Analyzer

Name an Entra group and see everything Intune sends to its members: configuration profiles, compliance, scripts and remediations, applications, app protection and configuration, enrolment restrictions, Autopilot and update profiles. Exclusions count as answers — a policy that deliberately does not reach this group is shown alongside the ones that do. Export as Markdown, CSV or a standalone HTML report.

🔮

Assignment what-if

Before you change a membership: pick a user or a device, name a group, and see the delta — policies gained, policies lost, applications that will install and applications that will be uninstalled. Joining brings the group's own parents with it; leaving only severs a direct edge, and a membership held through nesting says so instead of pretending it can be removed. An exclusion met by joining is shown as a loss, because joining a group can take policy away. Or put two to four groups side by side and see what each receives that the others do not. A simulation, not a promise — filtered assignments stay “may”, and reads only.

🩺

Assignment health

The assignments that exist and reach nobody, in one place — every finding the same shape of problem: something that looks configured and is not. Policies assigned to empty groups, which have never applied and never will; assignments naming deleted groups, which target nobody silently; unassigned policies; policies whose every assignment is an exclusion, so there is nothing to exclude from; a group both included and excluded on one policy, where the exclusion wins and the include reads as reach. Optionally, the deployments Graph reports as failing — for the surfaces that keep a cheap status, with the ones that do not named as unchecked rather than passed off as healthy.

✏️

Assignment editor writes to the tenant

Add or remove a group across many policies at once — the thing the portal makes you do one blade at a time. Device configurations, settings catalog, compliance and administrative templates; scripts and applications are deliberately out, because each would be a new write permission. The pipeline is the tool: read, dry-run with the group's name and member count, an automatic backup file of every assignment about to change, removals confirmed by typing the group's name — then the write, with each policy re-read first (someone else's edit is skipped as drifted, never overwritten) and read back after, so “done” is the tenant's word rather than a status code. No delete, no rename, ever.

🧩

Assignment filters writes to the tenant

Assignment filters are load-bearing and invisible: every “may reach it” in the Device analyzer is a filter in the way, and nothing in the portal shows what breaks if you change one. Every filter with its platform and rule, and — as its own optional read — per-filter usage: which assignments on which policies reference it, matched across the Group Analyzer's own surface table. Until that scan runs, the used-by column is absent, not zero. Then the write half, under the editor's rules: create, edit with a drift stop (a filter changed since you loaded it is refused, never overwritten), read-back after every write — and delete refused while anything references it, checked against the tenant at the moment of the click, because deleting a used filter silently widens every assignment that carried it.

Settings search

⚔️

Setting conflict scan

The same setting, configured to different values in two policies — found by setting identity, never by display name: the definition id in the settings catalog, definition-plus-category in administrative templates, the typed property within one policy type in device configurations. And one step past the tools that inspired it: a collision is only a conflict if the two policies can meet on a device, so every finding carries a verdict — can collide (overlapping reach), may collide (different groups can share members; a filter is in the way), or cannot (one side reaches nobody as assigned). Restricted AUs NEW

Create and manage restricted management administrative units — the only place in Entra where membership can be put out of reach of every tenant-wide role. Inside one, only a principal holding a role scoped to that unit may change the members; Global Administrator and Privileged Role Administrator can manage the unit but not what is in it. Ported from ENCA's T27 without its Conditional Access baseline. Writes to the tenant.

🔄

Group migration NEW

A group is made role-assignable for one side effect: only Global Administrator or Privileged Role Administrator may change its members. A restricted management administrative unit does that job better — it lets you name who may manage the group — and drops the role-assignable costs: the 500-per-tenant cap, no dynamic membership, no nesting control. The two can never be combined; a group that is both is a group whose members nobody can edit. Because isAssignableToRole is immutable this is a recreate, so the new group has a new object id: the tool repoints the four Intune surfaces it is already permitted to write, names every reference it cannot, and says out loud that anything outside Intune is invisible to it. The original is renamed aside as your rollback, never deleted. Writes to the tenant.

🔐 AppLocker builder & validator BETA

Scan a device, upload what the scan produced, edit the policy here, and export it as XML for a GPO or as a ready-to-import Intune custom profile. Everything is audited in the browser with the check set from Spencer Alessi's AppLockerInspector, and the Microsoft coverage table answers the question every lockdown discovers too late: can a standard user still run OneDrive, Teams, Edge and Office? Nothing is uploaded — the file is read in this tab and stays there. You can skip step 1 entirely and import a plain policy XML instead; the scan is what lets the tool see the ACLs a browser cannot.

1

Scan a device optional — but it is what makes the audit real

Run this on a clean reference machine — a freshly built image with your standard applications installed and nobody yet working in it. Not your own laptop. It reads directory permissions, signatures and the AppLocker event log, builds a publisher-first rule set from what it finds, and writes one .json bundle. It changes nothing on the device.

Why the machine matters more than the switches. The policy this produces says: everything on that machine is allowed, and nothing else is. From a clean image that is a baseline. From a device someone has used for two years it allows two years of accumulation — installers in Downloads, a dev toolchain, whatever a colleague once ran from a zip — which is the exact permission AppLocker is deployed to take away. The scan checks whether the machine looks clean and says so loudly if it does not, but it cannot refuse to run.

What the resulting policy allows: what is on the reference image · anything the Intune Management Extension delivers, named explicitly so trimming a default rule cannot silently kill software deployment · anything a local administrator runs. Everything else is blocked — a standard user's own profile above all.

How to run it, and what each switch is for

The normal run. Elevated PowerShell — unelevated it cannot read every DACL or the event logs, and the bundle records that the run was partial rather than pretending it was complete.

Set-ExecutionPolicy -Scope Process Bypass -Force
.\Invoke-TunoAppLockerScan.ps1

It writes three files next to itself: TunoAppLockerScan-<DEVICE>-<stamp>.json (upload this one), plus an Audit and an Enforce .xml for direct GPO use.

Include the per-user installs. OneDrive and Teams install into the user's profile, which is user-writable by definition — they are the applications a first AppLocker rollout breaks, every time.

.\Invoke-TunoAppLockerScan.ps1 -Scope System,ProgramFiles,ProgramData `
    -Path "$env:LOCALAPPDATA\Microsoft\OneDrive","$env:LOCALAPPDATA\Microsoft\Teams"

Switches worth knowing:

  • -Scope — which roots to walk: System, ProgramFiles, ProgramData, UserProfiles, Custom. Default is System,ProgramFiles.
  • -KnownAdmin — groups that are administrators here but are not in the local Administrators group, e.g. "CONTOSO\Workstation-Admins". Write access granted to them stops being reported as a hole.
  • -PublisherRuleGranularity — how specific the generated rules are, from Publisher to PublisherProductBinaryVersion. Default PublisherProductBinary.
  • -EventDaysBack — how far back to read the AppLocker logs. Default 30.
  • -DeepScan — report every writable directory instead of stopping at the first one on each branch. Slower, more evidence.
  • -SkipRuleGeneration — collect the evidence and let this tool build the rules instead.

Scan more than one machine. A laptop build and a kiosk build do not have the same holes. Run it on each, and work through the bundles one at a time.

5

Get it into Intune

AppLocker has no settings-catalog surface. The supported route is a Windows custom profile carrying one OMA-URI string per rule collection — which is exactly what the Intune profile tab produces.

Or do it yourself — three ways, from least to most automated

A · By hand in the portal. Intune admin center → Devices → Configuration → Create → Windows 10 and later → Templates → Custom. Then add one OMA-URI setting per collection, copying each omaUri and its value out of the JSON on the right. Data type is String. Tedious, but it needs no permissions beyond the portal.

B · Post the JSON with Graph. Download the profile from the Intune tab, then:

Connect-MgGraph -Scopes DeviceManagementConfiguration.ReadWrite.All
$body = Get-Content .\Win_-_Device_Security_-_AppLocker_(AuditOnly).json -Raw
Invoke-MgGraphRequest -Method POST -ContentType application/json `
    -Uri 'https://graph.microsoft.com/beta/deviceManagement/deviceConfigurations' `
    -Body $body

C · Let the converter script do it. Download the Policy XML tab (or use the Audit and Enforce XML the scan already wrote), then run Convert-TunoAppLockerToIntune.ps1. Offline it writes the profile JSON; with -Online it creates the profile in the tenant.

# No -Grouping: one is generated as AppLocker- and printed. Record it.

Then, in every case:

  1. Assign the AuditOnly profile first, to a small pilot group. Nothing here assigns anything for you — an AppLocker policy landing on a group by accident is not a recoverable afternoon.
  2. Make sure the Application Identity service is running on the targets, or AppLocker does nothing and logs nothing. Set it to start automatically via an Intune configuration profile or a remediation script.
  3. Leave it in audit long enough to cover a month-end, a patch cycle and a new starter. Collect events 8003 and 8006 — the things that would have been blocked.
  4. Re-run the scan, upload the new bundle here, and work the blocked list down to nothing.
  5. Only then move to Enforced — by editing the profile you already have, not by assigning a second one. See the grouping note below; two live profiles is the trap.

One profile, one grouping, edited in place. The grouping is a CSP node name, and Microsoft's guidance is that it should be unique — "Delete/unenrollment is not properly supported unless Grouping values are unique… The best practice is to use a randomly generated GUID." Two profiles sharing a grouping write the same OMA-URIs, so unassigning one can delete the nodes the other still depends on. So: give the profile a grouping of its own (a GUID is ideal), and go from audit to enforce by changing that profile's values rather than deploying a second profile beside it.

Deploying does not clear what came before. Every path adds rather than replaces — the CSP keeps one node per grouping and type until something explicitly deletes it, Group Policy merges rules from every linked GPO, and local policy persists until cleared. A collection your new policy simply omits keeps running. Upload a scan and the audit will name any collection the device is running that this policy does not contain.

It reboots. The AppLocker CSP's Policy nodes carry automatic reboot behaviour, on apply and on delete. Neither deploying nor removing is quiet — plan both for a window.

Keep a way back. Removing the assignment removes the policy, but a device that cannot run the management agent cannot be told that. Test the removal path on the pilot group before the estate depends on it.

🔗 Group Analyzer BETA

A group is a shared handle: one admin targets a compliance policy at it, another assigns four applications, a third puts an Autopilot profile on it — and then somebody adds a user, and none of that is visible at the moment of the change. This reads it back out of the tenant. Intune surfaces after Ugur Koc's Get Group Assignments; the analysis machinery is ENCA's Group Analyzer. Reads only — each surface asks for its own scope on the click, and nothing is written or stored.

Intune only, on purpose. Where a group is used in Conditional Access, group-based licensing, directory roles or access packages is the same question asked of Entra, and answering it needs permissions TUNO has no reason to hold. That is ENCA's Group Analyzer, which is signed in for exactly that.

Off by default because it is loud and it is the same answer for every group: a tenant-wide assignment is not about this group. It is on the list because the question an admin is usually asking — what actually lands on these devices — has a bigger answer than the group's own assignments, and nothing else on this page would tell them so.

A sweep reads each surface once and matches every group against it, so the cost barely grows with the number of groups. R17 🔁 Tenant sync — copy configuration between tenants would write to the tenant

After TenuVault's sync (Ugur Koc, MIT). Take configuration from one tenant and create it in another — whole types or named policies — for the jobs nobody has a good answer to today: standing up a new customer from a known-good baseline, keeping a pilot tenant and production in step, and lifting a policy set out of a tenant that is being decommissioned. A managed-service provider does this by hand, in the portal, once per tenant, and it is the single most repetitive thing in the job.

Two routes, and the difference is not a detail. Backup-mediated: export tenant A with R08, sign into tenant B, restore the archive — which is really R09 with a file that came from somewhere else, needs one sign-in at a time, and leaves an artefact on disk that says exactly what was copied. Live: both tenants signed in at once, read from A and write to B in one act. TenuVault supports both and so should this — but the backup-mediated route is the one that should exist first, because it is the one that cannot surprise you.

THE LIVE ROUTE BREAKS AN ASSUMPTION THE WHOLE APP RESTS ON. TUNO holds one signed-in account. Every safety rule it has — the collision stop, the member count before an assignment, the tenant named in a backup manifest — assumes you are looking at the tenant you are changing. Live sync means two accounts in two tenants held at the same time, and a mistake is no longer a duplicate policy in the tenant in front of you; it is configuration created in the wrong tenant, quite possibly a customer's. MSAL can hold two accounts and the browser can carry both tokens, so this is buildable — but it needs the source and the target named, in words, on screen, at every step, and a confirmation that types the target tenant's domain rather than clicking a button. It is the sharpest edge on this roadmap and it should be built last.

What cannot travel, said here rather than found at the far end. Assignments do not copy — a group id means nothing in another tenant, and one that happens to resolve there is worse than one that fails, so they are dropped and the report says which policies arrived unassigned. Secrets do not copy, for the same reason they are absent from a backup: Graph never returned them. Anything referencing a certificate, a Wi-Fi key or an encrypted setting arrives configured-but-incomplete and must be finished by hand, and the report will name every one. Objects that cannot be recreated at all — default and singleton enrolment configurations — are reported as skipped rather than attempted, which TenuVault learned the same way.

And the shortcut that will be tempting here is not available. TenuVault signs in with no app registration at all by borrowing Microsoft's own Graph PowerShell client id — sound for a locally installed binary, and impossible for a web page: that application is registered as a public client with a localhost redirect, a browser needs a redirect URI of type single-page application, and Entra refuses the cross-origin token redemption outright. It could not be added either, since the application is Microsoft's. It would also be wrong if it worked — the consent record in a customer's tenant would name Graph PowerShell rather than TUNO, and every read would appear in the sign-in log as Microsoft's tool rather than this one. SECURITY.md sets out the reasoning; the short version is that syncing between tenants means two consent records, both of which have to be real.

The rules from R09 apply unchanged, plus one of TenuVault's own: create only, never patch or delete; a name prefix on everything created; a dry run listing every operation before anything is sent. And a prefix-free sync is refused when source and target are the same tenant — because at that point it is not a sync, it is a silent duplication of your own configuration, and TenuVault refuses it for exactly that reason.

What TUNO is

TUNO — Tenant Utilities for iNtune Operations is ENCA's sister tool (enca.limon-it.nl): the same idea — static files running entirely in your browser, minimal delegated Graph permissions asked per tool, nothing stored server-side because there is no server — applied to Intune and endpoint security instead of Conditional Access.

🔐 AppLocker builder & validator

Reads NOTHING from your tenant: what you upload is parsed in this tab, audited with the AppLockerInspector check set, evaluated against a catalog of Microsoft apps (per-user OneDrive is the one everybody breaks), and exported as policy XML, an Intune custom profile, or a Markdown report. Rule evaluation here is a faithful model — deny beats allow, exceptions carve back out, macros expand, publisher fields match — not the AppLocker engine itself. The five steps. ① Download Invoke-TunoAppLockerScan.ps1 and run it elevated on a representative device. ② Upload the .json bundle it writes. ③ Work through the findings and the coverage table, fixing what needs fixing. ④ Export the policy XML for a GPO, or the Intune custom profile. ⑤ Assign the AuditOnly profile to a pilot group, wait, re-scan, and only then enforce.

Why there is a PowerShell script at all. A browser cannot read a directory ACL, verify an Authenticode signature or open an event log — and those three facts are most of what decides whether an AppLocker policy is sound. A rule allowing %PROGRAMFILES%\* is only as strong as the permissions underneath it, and the XML does not say what those are. The scan does, and the tool marks every verdict that came from it with 🛰 so you can see which half of the analysis proved what. Skip the scan and the tool still works on a plain policy XML; it just cannot tell you about the holes it cannot see.

The scripts are served from this site (/scripts/), so the copy you download always matches the build you are looking at. They are read-only on the device: neither one applies a policy, touches the local GPO, or starts the Application Identity service. Source and the full switch reference are in scripts/README.md.

🏷 AppLocker groupings — what they are, and why yours must be unique

What a grouping is. When Intune delivers AppLocker, each rule collection is written to a CSP node whose address includes a name you choose: ./Vendor/MSFT/AppLocker/ApplicationLaunchRestrictions/{Grouping}/EXE/Policy. That name is the policy's identity on the device — not a label, an address. Everything else about groupings follows from that one fact.

The why, in three consequences. ① Different groupings merge. A device holding groupings A and B enforces both — deny beats allow across all of them, and a collection missing from B does not switch off its counterpart in A. Deploying a second grouping therefore never replaces the first; it stacks on it. ② Same grouping means same address, so two Intune profiles sharing a grouping write to identical nodes — and Microsoft's own warning is that removal then breaks: “Delete/unenrollment is not properly supported unless Grouping values are unique… the best practice is to use a randomly generated GUID.” Unassign one profile and the CSP can delete the nodes the other still depends on, leaving orphaned policy nothing in the portal points at. ③ Apply and delete both reboot the device — the CSP's Policy nodes carry automatic reboot behaviour, so neither rollout nor rollback is quiet.

How to use it, then. One profile, one grouping, a GUID — and you move from audit to enforce by editing that profile in place, never by assigning a second profile beside it. When migrating a device that already carries policy: unassign the old profile first (Intune sends the CSP delete), run Clear-TunoAppLockerPolicy.ps1 to sweep what unassignment leaves behind, then deploy under a new grouping. The cleanup names every MDM grouping it finds on the device — the supported removal for a live grouping is unassigning its profile, and -RemoveMdmGroupings exists for the orphans the shared-grouping bug leaves. T01 prefills the house format — AppLocker-<guid>, unique like the GUID Microsoft asks for, recognisable in logs unlike a bare one — with a ↻ button to mint a fresh identity for a genuinely new deployment; the converter generates the same when -Grouping is omitted. Resist naming groupings pilot or production: that distinction lives in the assignment and the mode, and a hand-reusable word is exactly what produces two profiles sharing a grouping. The Intune tab warns when it sees one, and the carry-over findings show what other groupings already put on the device.

🔮 Assignment what-if

What would change if this user or device joined, or left, that group — asked while the change is still cheap to reverse. Memberships today are read transitively, the hypothetical set is built (joining a group adds everything it is nested under; leaving severs one edge and rebuilds what remains), and every assignment surface is read once with each policy's effect computed under both sets. The difference is the answer. Reads only.

Four states, not two — gained, lost, pre-excluded, unchanged — because joining a group can take policy away: an exclusion met by joining is a loss, and that is the most surprising row this tool produces. A filtered assignment stays may in both directions; a dynamic group cannot be joined by hand, so that answer is labelled conditional on the rule; an app with intent uninstall that starts to apply says will be uninstalled, not gained.

🩺 Assignment health

The assignments that exist and reach nobody, in one place: assignments into empty groups, dangling references to groups the directory no longer has, unassigned policies, excluded-only policies, one group both included and excluded on the same policy (the exclusion wins), and optionally failed deployments where Graph keeps cheap status. Every finding is the same shape of problem — something that looks configured and is not.

Findings, not a score — whether an empty group is a mistake or a landing zone prepared for next quarter is not something a tool can know. And unknown is never clean: a group that could not be peeked is unknown rather than empty, a surface whose status Graph keeps out of reach is named as unchecked rather than passed off as healthy.

✏️ Assignment editor writes to tenant

Bulk assignment changes — add an include, add an exclusion, or remove a group across many policies at once, the thing the portal makes you do one blade at a time. This is the tool in TUNO that writes at scale, and the pipeline is the point: read → plan → backup → confirm → apply → verify, enforced by the screen. The dry run names every group with its member count, the backup is automatic and applying stays locked until it exists, removals are confirmed by typing the group's name, and the write scope is asked for at the apply click — never at sign-in.

What it refuses and what it will not do. An include onto a policy that excludes the group, or an exclusion onto one that includes it, is refused as a contradiction rather than applied. A policy whose assignments changed since the plan was made is skipped as drifted rather than overwritten. Every write is verified by reading the tenant back, writes never retry, and there is no delete and no rename — neither belongs in a browser tool whose whole argument is that it cannot do much harm.

🔦 Settings search

“Which policies configure BitLocker, and to what value?” — answered from the setting definitions rather than the policy names. The settings-catalog definition catalog (roughly seventeen thousand entries, Microsoft's rather than the tenant's) is read once and searched as you type; a second, optional read of the tenant's own policies lets each result say who sets it and to what.

Until that second read runs, the usage column is absent — not empty. “Nobody sets this” and “nobody looked” are different answers, and the screen and the export both say which one you have. Values pass the documenter's redaction gate, because a settings search is exactly the tool somebody uses to hunt for “password”, and a result table printing secrets would be a disclosure engine with a search box.

🖥 Device analyzer

The Group Analyzer asks what a group receives. This asks what one device receives, and why — walking the same nine assignment surfaces backwards through the groups the machine is in, the groups its primary user is in, and the tenant-wide targets that name no group. Every row names the relationship that put it there. The device is found by name, serial, either of its two GUIDs — or by its primary user: a UPN, the exact display name, or the user's object id resolves to their machines straight off the enrolment record, no extra permission, and a user with more than one device gets a pick list of clickable cards. Reads only.

Read the check-in first. Every assignment here is what Intune intends; what the device has is whatever it collected the last time it talked to the service. A policy assigned ten minutes ago has not reached a machine that last synced yesterday, and no amount of correct assignment data changes that — so the check-in time is the first thing on the page.

Three answers this tool refuses to guess at. ① A filtered assignment may or may not reach this device: the rule is evaluated by the service against inventory a browser cannot see, and Graph offers no call that answers it. Those rows say may reach it. ② A policy the device has not reported on has state unknown, not compliant — and where a reported state cannot be tied to a policy with certainty, because two policies share a name, that is unknown too. ③ Where a policy is included through one group and excluded through another, an exclusion wins in Intune and the row says excluded — except when the two arrive through different kinds of group, device against user, where whether the exclusion applies depends on how the policy is targeted and the assignment does not say. That one is called a conflict and left to the portal.

Tenant-wide assignments are shown by default here, unlike in the Group Analyzer. All Devices reaches this machine whatever else is true, so hiding those rows would hide policy it is definitely getting. All Users lands on the person, so a device with no primary user does not receive them — and the row says so rather than being dropped.

🛡 Intune RBAC

Every Intune role definition with its assignments, members, scope and scope tags, on one page. After Ugur Koc's PowerShell script (MIT). Every role carries a ⚙ permissions button — the actions it allows, grouped the way the portal groups them, read on the click from the role definition; Intune RBAC is an allow list, so anything not named is not granted. A member that is a group carries a 👥 members button — who effectively holds the role through it, transitive so nesting is flattened, users only since devices and service principals do not hold Intune RBAC, capped at 500 with the true total shown. Read on the click, never during the run, and the answer is live rather than from the report's moment. Reads only: DeviceManagementRBAC.Read.All, plus User.Read.All and Group.Read.All to turn member GUIDs into names and expand a group.

Read the first line on the screen before you rely on this. It is Intune RBAC only. Global Administrator and Intune Administrator are Entra directory roles, they grant full access to Intune, and Graph does not return them from deviceManagement/roleAssignments. Nothing this tool can ask for would show them, so it says so rather than letting the report pass for a complete answer.

Empty roles are a toggle. A role with no assignments is one membership change from being a live grant, so it is a fact worth seeing — off by default because most tenants use a handful of the built-in roles, and switching it on re-renders what was already read rather than asking the tenant again.

The flags are observations and there is no score. An assignment scoped to all devices; a broad built-in role with a lot of members, at a threshold the screen states because it is arbitrary; a role whose members are all one group, where whoever can change that group can grant the role without holding it. Whether any of those is wrong depends on things the tool cannot see.

🕓 Change audit

Reads the tenant's own audit log and says who changed what, when, from where, and which fields moved. Two views over one read: policy changes with a severity on each, and all events with actor / activity / category / result filters. Filters apply to what has already been read, so changing one costs nothing. Reads only.

Thirty days is the whole log. Intune keeps audit data for thirty days and then it is gone from the service — not archived, not slower to reach. There is deliberately no ninety-day window: it would return an empty answer for days thirty-one to ninety that looks exactly like a quiet tenant.

Wildcards are wildcards. In the actor and activity boxes, admin* means starts-with and *Delete* means contains. A term with no wildcard is treated as contains, which is what someone typing into a filter box means — but if you write a wildcard it is honoured exactly, rather than being quietly widened.

An event with no detail is not an event with no changes. Some audit records carry no modifiedProperties at all — a create, usually, or a service-initiated action. Those say so explicitly rather than rendering as an empty list, because "nothing changed" and "the log does not say" are different answers.

📦 Backup configuration

Reads the configuration surface and writes one .zip in this tab. Nothing is uploaded and nothing is stored — the archive is built in memory and handed to your browser's download. One permission, read-only, asked on the click.

Interoperable on purpose. The folder names and file names match the PowerShell original exactly, because restore in both his script and TUNO's R09 is driven by folder names. A tidier scheme would have cost that, and interoperability is worth more.

Two things it cannot contain. Graph never returns secret values, so encrypted OMA-URI settings, passwords and certificate payloads come back as references and must be re-entered by hand after a restore — that is a property of Graph, not of this tool. And a script saved without its body can be read but not put back; leaving bodies out is offered because they can be large, and every file it affects is marked in the manifest.

Missing beats wrong. An object whose detail could not be read is left out of the archive rather than written without it, because a policy restored with the right name and no settings looks like it worked. An area that could not be read at all marks the whole archive partial, on screen and in the manifest.

📄 Configuration documenter

Reads thirteen configuration surfaces once and gives you two things: a filterable list of every policy in the tenant with its settings expandable underneath, and a document you can hand to somebody. Filters apply to what has already been read, so changing one costs nothing — and they apply to the exports too, so you can narrow to exactly what you need to circulate.

Secrets are redacted and there is no switch. Script bodies, certificates, passwords, pre-shared keys and encrypted OMA-URI values are replaced with a marker: the document records that a value is set without carrying it. This is the artefact most likely to be emailed, and a disclosure in one cannot be recalled.

Clicking a policy opens a popout. Expanding in place was wrong for a list this long — a settings-catalog policy carries twenty-odd rows, so opening one pushed everything else off the screen and closing it lost your place. Escape, the Close button and the backdrop all dismiss it.

The exports follow the SELECTION, not the filter. Two different jobs: the filter narrows what you are looking at, the tick boxes decide what you are sending. That is what lets you filter to find three policies, tick them, clear the filter, and still export three. Everything is selected after a read; with nothing selected the export buttons disappear, because a button that would produce an empty document is worse than no button.

A partial document says which kind of partial. Every export header states how many of how many objects it holds and whether a person chose them or a filter produced them — “I picked these twelve” and “a platform filter left twelve” are different claims, and neither is “this is the tenant”.

Unknown is stated, not hidden — but differently from the backup tool. A section that could not be read is named as unreadable and is absent from the document. A single policy whose settings could not be read is still listed, with the gap stated, because a document is for reading rather than restoring: knowing a policy exists and that its configuration could not be retrieved is worth more than the policy silently disappearing.

Sign-in is a SPA authorization-code + PKCE flow with no client secret — the same model as ENCA, documented in SECURITY.md. You can run TUNO on your own single-tenant app registration: New-TunoAppRegistration.ps1 -SingleTenant.
