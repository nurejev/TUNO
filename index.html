🔐 AppLocker builder & validator BETA

Scan a device, upload what the scan produced, edit the policy here, and export it as XML for a GPO or as a ready-to-import Intune custom profile. Everything is audited in the browser with the check set from Spencer Alessi's AppLockerInspector, and the Microsoft coverage table answers the question every lockdown discovers too late: can a standard user still run OneDrive, Teams, Edge and Office? Nothing is uploaded — the file is read in this tab and stays there. You can skip step 1 entirely and import a plain policy XML instead; the scan is what lets the tool see the ACLs a browser cannot.

1

Scan a device optional — but it is what makes the audit real

Run this on a representative machine — your standard image, with the applications people actually use installed. It reads directory permissions, signatures and the AppLocker event log, builds a publisher-first rule set from what it finds, and writes one .json bundle. It changes nothing on the device.

⭳ Invoke-TunoAppLockerScan.ps1

No Sysinternals needed. Write access is worked out natively from each directory's DACL, with Deny entries honoured. AaronLocker and the walkthroughs based on it shell out to AccessChk.exe and parse its output; this does not, which is why there is nothing else to download — and its own alternate-data-stream check ORs the rights across every matching entry without looking at whether one of them is a Deny, so a Deny there reads as a grant. Nothing here is downloaded or executed from anywhere but this site.

How to run it, and what each switch is for

The normal run. Elevated PowerShell — unelevated it cannot read every DACL or the event logs, and the bundle records that the run was partial rather than pretending it was complete.

Set-ExecutionPolicy -Scope Process Bypass -Force
.\Invoke-TunoAppLockerScan.ps1

It writes three files next to itself: TunoAppLockerScan-<DEVICE>-<stamp>.json (upload this one), plus an Audit and an Enforce .xml for direct GPO use.

Include the per-user installs. OneDrive and Teams install into the user's profile, which is user-writable by definition — they are the applications a first AppLocker rollout breaks, every time.

.\Invoke-TunoAppLockerScan.ps1 -Scope System,ProgramFiles,ProgramData `
    -Path "$env:LOCALAPPDATA\Microsoft\OneDrive","$env:LOCALAPPDATA\Microsoft\Teams"

Switches worth knowing:

  • -Scope — which roots to walk: System, ProgramFiles, ProgramData, UserProfiles, Custom. Default is System,ProgramFiles.
  • -KnownAdmin — groups that are administrators here but are not in the local Administrators group, e.g. "CONTOSO\Workstation-Admins". Write access granted to them stops being reported as a hole.
  • -PublisherRuleGranularity — how specific the generated rules are, from Publisher to PublisherProductBinaryVersion. Default PublisherProductBinary.
  • -EventDaysBack — how far back to read the AppLocker logs. Default 30.
  • -DeepScan — report every writable directory instead of stopping at the first one on each branch. Slower, more evidence.
  • -SkipRuleGeneration — collect the evidence and let this tool build the rules instead.

Scan more than one machine. A laptop build and a kiosk build do not have the same holes. Run it on each, and work through the bundles one at a time.

or skip it — upload a policy XML you already have
2

Upload what the scan wrote — the .json bundle.

It carries the generated rule set, the policy the device was really running, the directories a standard user can write to, the unsigned binaries sitting in them, and what AppLocker has already blocked. The tool loads the generated AuditOnly policy by default and you can switch to either of the others once it is open.

No scan? A plain policy XML works too — a GPO export (Group Policy Management Editor → Application Control Policies → AppLocker → right-click → Export Policy…) or Get-AppLockerPolicy -Effective -Xml > policy.xml. You lose the ACL and event evidence, which is exactly the part a browser cannot work out for itself.

Or load the sample policy to see what the audit and the Microsoft coverage check produce.

AppLockerPolicy.xml

DLL always ships as NotConfigured. AppLocker evaluates every DLL load — enforced it cripples the device, and even AuditOnly buries the event log. The rules are in the profile, documented and inert.

5

Get it into Intune

AppLocker has no settings-catalog surface. The supported route is a Windows custom profile carrying one OMA-URI string per rule collection — which is exactly what the Intune profile tab produces.

Or do it yourself — three ways, from least to most automated

A · By hand in the portal. Intune admin center → Devices → Configuration → Create → Windows 10 and later → Templates → Custom. Then add one OMA-URI setting per collection, copying each omaUri and its value out of the JSON on the right. Data type is String. Tedious, but it needs no permissions beyond the portal.

B · Post the JSON with Graph. Download the profile from the Intune tab, then:

Connect-MgGraph -Scopes DeviceManagementConfiguration.ReadWrite.All
$body = Get-Content .\Win_-_Device_Security_-_AppLocker_(AuditOnly).json -Raw
Invoke-MgGraphRequest -Method POST -ContentType application/json `
    -Uri 'https://graph.microsoft.com/beta/deviceManagement/deviceConfigurations' `
    -Body $body

C · Let the converter script do it. Download the Policy XML tab (or use the Audit and Enforce XML the scan already wrote), then run Convert-TunoAppLockerToIntune.ps1. Offline it writes the profile JSON; with -Online it creates the profile in the tenant.

⭳ Convert-TunoAppLockerToIntune.ps1 
# Offline — write the JSON for both modes, review before anything touches a tenant
.\Convert-TunoAppLockerToIntune.ps1 `
    -XmlPath .\AppLockerRules-Audit-20260819-1530.xml,.\AppLockerRules-Enforce-20260819-1530.xml `
    -Grouping 'Pilot' -DisplayName 'Win - Device Security - AppLocker'

# Online — create the audit profile in the tenant
.\Convert-TunoAppLockerToIntune.ps1 -Online -TenantId 'contoso.onmicrosoft.com' `
    -XmlPath .\AppLockerRules-Audit-20260819-1530.xml `
    -Grouping 'Pilot' -DisplayName 'Win - Device Security - AppLocker'

Then, in every case:

  1. Assign the AuditOnly profile first, to a small pilot group. Nothing here assigns anything for you — an AppLocker policy landing on a group by accident is not a recoverable afternoon.
  2. Make sure the Application Identity service is running on the targets, or AppLocker does nothing and logs nothing. Set it to start automatically via an Intune configuration profile or a remediation script.
  3. Leave it in audit long enough to cover a month-end, a patch cycle and a new starter. Collect events 8003 and 8006 — the things that would have been blocked.
  4. Re-run the scan, upload the new bundle here, and work the blocked list down to nothing.
  5. Only then assign the Enforced profile — same grouping, so it replaces the audit one on the device rather than sitting alongside it.

Keep a way back. Removing the assignment removes the policy, but a device that cannot run the management agent cannot be told that. Test the removal path on the pilot group before the estate depends on it.

Now shipped & shipping

R01 🔐 AppLocker builder & validator live · build 1 BETA

Web-based AppLocker policy analysis after Spencer Alessi's AppLockerInspector: import the XML, get the weak/misconfigured/risky settings with severity, reason and recommendation — plus the check the PowerShell original does not have: a Microsoft app coverage table that verifies OneDrive (per-user!), Teams, Edge, WebView2, Office click-to-run, the Intune agent and friends are actually allowed to run for a standard user, with one-click publisher-first fixes and XML export back into the GPO.

Next

R02 📊 Secure Score visualizer

Read the tenant's Microsoft Secure Score over Graph (security/secureScores and the control profiles) and make it explorable: score over time, per-category breakdown, which improvement actions buy the most points for the least user pain, and what changed since last month — with a Markdown export for the monthly report. Asks for SecurityEvents.Read.All on the click, ENCA-style incremental consent, and reads only.

R04 🔗 Group Analyzer — ENCA's T19, merged with Ugur Koc's group assignment scan

ENCA's Group Analyzer already reads where an Entra group is used across 23 services; the TUNO port turns the telescope around and leads with the Intune areas — enrolment restrictions, compliance, configuration profiles, scripts and remediations, app protection and configuration, app assignments, Autopilot, Windows update rings — with per-area consent, the unused-groups sweep, parent-group inheritance and Markdown/HTML/CSV export carried over. The Entra areas stay, as context rather than headline: an Intune admin asks “what lands on the devices in this group”, and the answer must open with Intune.
Two things come from Get Group Assignments (Ugur Koc) that ENCA's version does not have, and both change the answer rather than decorating it. Exclusions are read as assignments: a group named in an exclusionGroupAssignmentTarget is listed alongside the inclusions and marked as an exclusion, because “this policy does not reach you” is the same question as “this policy reaches you” and a report that only shows one of them is wrong half the time. And tenant-wide targets are offered as a toggle — All Users and All Devices land on the group's members too, so the effective surface is bigger than the group's own assignments, and an admin sizing up a change needs to see that without being made to guess. TUNO adds what the script's own notes say it does not do: nested group inheritance, so a policy assigned to a parent shows up on the child.

R05 🕓 Change audit — ENCA's T16, pointed at Intune

ENCA's Change audit reads the directory audit log for Conditional Access edits with a field-level diff of what moved. The TUNO port points the same machinery at deviceManagement/auditEvents: who changed which compliance policy, configuration profile, app assignment, script or enrolment setting, when, from where — the same 1/4/24-hour incident windows and 7/30/90-day review windows, kind/action filters, field-level before/after diff where the audit record carries it, and Markdown export. Reads only, DeviceManagementApps.Read.All / DeviceManagementConfiguration.Read.All asked on the click.
One tool, two views, after Ugur Koc's two scripts against that endpoint. Policy Changes Monitor is the policy changes view: filtered to configuration-policy activity, with the before/after pairs the audit record already carries and a severity read off the activity — a delete or a failure outranks a create, a create outranks an assignment change. Get Intune Audit Logs is the all events view: every category, filtered by actor, activity and result. They are one tool because they are one Graph read — two tiles would be two copies of the same paging, the same throttling and the same export. Three fixes ride along: the two scripts window the same endpoint two different ways (a full UTC timestamp in one, a bare date in the other) and TUNO uses the timestamp in both; the categories are read from the tenant's own data rather than a fixed list that includes values Graph never emits; and the policy view is not capped at five rows.

R03 🖥 Intune device analyzer

The tuno.md original: pick a device and see which groups it is in, which policies land on it and why, and which apps it gets — the Intune counterpart of ENCA's per-user policy views. It is R04 read from the other end: the Group Analyzer answers “what does this group receive”, and the same assignment graph answers “why did THIS device get that policy” once you walk it backwards through the device's group memberships, its filters and the tenant-wide targets. Compliance state and the last check-in sit next to the answer, because the second question is always whether the policy has actually landed yet. Reads DeviceManagementManagedDevices.Read.All alongside R04's scopes.

R07 🛡 Intune role assignments

After Ugur Koc's Get Intune Role Assignments. Who can change Intune, in one page: every role definition, built-in and custom, each assignment under it, the scope tags it is limited to, and the users and groups in it resolved to names. The portal makes you click into each role one at a time, which is why nobody audits this. Empty roles are shown on request — a role with no assignments is a fact worth seeing, not a row worth hiding. Reads DeviceManagementRBAC.Read.All, plus User.Read.All / Group.Read.All to turn member GUIDs into names; the resolution goes through directoryObjects/getByIds in batches of a thousand rather than the script's probe-users-then-groups loop, which costs up to two round trips per member.

R08 📦 Backup Intune configuration

After Ugur Koc's Backup Intune Configuration. Read the configuration surface — device configuration profiles, settings catalog policies with their settings, compliance policies with their scheduled actions, ADMX policies with their definition values, and platform scripts with their bodies — and write one .zip in the browser, in the same folder layout the PowerShell original produces so the two are interchangeable. Reads only: DeviceManagementConfiguration.Read.All, asked on the click. The manifest carries more than the original's object counts — every file is indexed with its type, its Graph surface and its source tenant, because a backup you cannot identify six months later is an archive of anonymous JSON. Two things the original documents and TUNO repeats rather than hides: Graph never returns secret values, so encrypted OMA-URI settings, passwords and certificates come back as references and have to be re-entered; and a backup taken without script bodies cannot restore scripts.

Later

R06 📄 Tenant documentation — Markdown, Word and PDF

After Ugur Koc's IntuneDocumentation. The document an auditor asks for and nobody has: every configuration surface in the tenant, laid out as readable prose and tables rather than a JSON dump — settings catalog, device configurations, administrative templates, compliance, app protection and configuration, security baselines, scripts and remediations, update rings, enrolment, Autopilot, assignment filters, scope tags — with assignments resolved to group names and a cover page, contents and per-section source endpoints. Exports as Markdown (for a wiki), Word (for the auditor who will edit it) and PDF (for the one who will not). Reads only. The original is a Next.js app with a server tier that holds the token and calls Graph on the browser's behalf; TUNO has no server, so the collection has to be reimplemented client-side — which is also the honest version of “runs in your browser”. Secret-bearing fields are redacted the same way the original redacts them.

R09 📥 Restore Intune configuration

After Ugur Koc's Restore Intune Configuration. Take an R08 archive and put a single policy, a selection, or the whole thing back into a tenant. This is the second thing in TUNO that writes, and it gets T01's rules rather than the script's. The original never checks whether the object already exists — it always creates, so a re-run silently produces a second copy of every policy, and its own notes say so. TUNO reads first: a policy whose name already exists stops the restore for that object and offers overwrite, skip or rename as a decision you make, not a prefix you hope you remembered. DeviceManagementConfiguration.ReadWrite.All is asked for on the click and never at sign-in. A dry run lists every operation before anything is sent, including the child writes the original's -WhatIf never shows — the ADMX definition values and the assignments. Assignments stay off unless asked for, and are checked against the target tenant first, because a group GUID from the source tenant either does not exist there or, worse, names a different group.

R10 🔑 LAPS viewer admin-side — not the self-service portal

Inspired by Daniel Fraubaum's LAPS Self-Service Portal, and deliberately not a port of it. His design cannot be built as a browser-only tool, and the reason is worth stating rather than discovering. Reading a Windows LAPS password with delegated permission requires the signed-in user to hold Cloud Device Administrator or Intune Service Administrator — precisely the roles an ordinary employee retrieving their own laptop's password does not have. And DeviceLocalCredential.Read.All is tenant-wide with no per-device scoping, so “only your own device” is only true if something the user cannot reach enforces it. His portal puts that somewhere a browser cannot: an Azure Function holding an app-only token behind its own Managed Identity. That is the correct architecture for self-service, and TUNO has no server to put it in.
What TUNO can honestly be is the helpdesk-side tool: for staff who already hold the role, find a device and read its password without three portal blades, with the retrieval landing in the tenant's own audit log. Same problem, the half of it that fits a static site.

❓ Help

What TUNO is

TUNO — Tenant Utilities for iNtune Operations is ENCA's sister tool (enca.limon-it.nl): the same idea — static files running entirely in your browser, minimal delegated Graph permissions asked per tool, nothing stored server-side because there is no server — applied to Intune and endpoint security instead of Conditional Access.

🔐 AppLocker builder & validator

Reads NOTHING from your tenant: what you upload is parsed in this tab, audited with the AppLockerInspector check set, evaluated against a catalog of Microsoft apps (per-user OneDrive is the one everybody breaks), and exported as policy XML, an Intune custom profile, or a Markdown report. Rule evaluation here is a faithful model — deny beats allow, exceptions carve back out, macros expand, publisher fields match — not the AppLocker engine itself. Test in AuditOnly before enforcing, always.

The five steps. ① Download Invoke-TunoAppLockerScan.ps1 and run it elevated on a representative device. ② Upload the .json bundle it writes. ③ Work through the findings and the coverage table, fixing what needs fixing. ④ Export the policy XML for a GPO, or the Intune custom profile. ⑤ Assign the AuditOnly profile to a pilot group, wait, re-scan, and only then enforce.

Why there is a PowerShell script at all. A browser cannot read a directory ACL, verify an Authenticode signature or open an event log — and those three facts are most of what decides whether an AppLocker policy is sound. A rule allowing %PROGRAMFILES%\* is only as strong as the permissions underneath it, and the XML does not say what those are. The scan does, and the tool marks every verdict that came from it with 🛰 so you can see which half of the analysis proved what. Skip the scan and the tool still works on a plain policy XML; it just cannot tell you about the holes it cannot see.

The scripts are served from this site (/scripts/), so the copy you download always matches the build you are looking at. They are read-only on the device: neither one applies a policy, touches the local GPO, or starts the Application Identity service. Source and the full switch reference are in scripts/README.md.

Security model

Sign-in is a SPA authorization-code + PKCE flow with no client secret — the same model as ENCA, documented in SECURITY.md. You can run TUNO on your own single-tenant app registration: New-TunoAppRegistration.ps1 -SingleTenant.
