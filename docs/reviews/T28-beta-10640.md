# T28 MDE rollout — beta 10640

Date: 2026-09-30. T28 0.9. Promotion queue item 202.

## Why

**Mihai:** "An option to split the adding of the pilot group in 4 even batches of users and devices."

The mockup (`t28-pilot-batches-mockup.html`) offered two places for a batch:

- **A.** Users go straight into the waves, and the device group follows them.
- **B.** Four batch groups per kind.

He picked **A**.

## How it works (`MdeMembers`)

| Part | What it does |
| --- | --- |
| Which pilots | Pilots in `cfg.members.batched`. The default is `NL-Breda`, set with one tick per pilot on its batch panel and kept per tenant. `batchCount` is 4. |
| Who is batched | The pilot group's users, minus those already in the user wave through another nested group. A Breda user is in NL as well; they are counted and named, not batched. |
| The split | 4 even parts: sizes differ by one at most (48 → 12 each; 10 → 3, 3, 2, 2), sorted by UPN. A user's Windows devices (Intune primary user) go with them. |
| What is "in" | The batchable users who are **direct** members of the user wave. `readInput` now reads each wave's direct users. |
| The next batch | Tops up the first part that is not full yet, cut from whoever is still left. Users who join or leave the group in between are counted in. For example: 10 users, batch 1 in, one user leaves → parts become 3, 2, 2, 2, batch 1 stays in, and batch 2 has 2 users to add. |
| A batch (`planBatch`) | 1. Its users go straight into the user wave (`memberKind: user`).<br>2. Their devices go into the pilot's device group, which is created first if needed (owner: you).<br>3. The device group is nested in the device wave if it isn't yet.<br>Devices with no Entra object, and excluded devices (10639), are left out with the reason. |
| The device group follows its users | While batching, `compute` wants only the devices of users already in the wave. The regular sync therefore never fills ahead of a batch, and the device detail says "🧪 waits for batch N". |
| The regular sync | Never nests a batched pilot's user group. It says why. |
| Finish (`planFinish`) | After the last batch:<br>1. Nest the pilot group into the user wave, so new users flow in.<br>2. Take the direct users out, since they are in through the group now. This is a typed REMOVE.<br>If Finish runs early, the plan warns that the rest arrive at once. |
| Finished | The group is nested. Every device of the group is wanted again, as for any other country. |

Every batch is a 👥 plan: dry run, tick to confirm, apply on the ledger, read back (users as users), and undo from 📜. `patchInput` moves the wave's direct users, so the panel moves on without a re-read.

## Screen

- **The pilot row** says "🧪 pilot · in batches". Its "In the wave" cell reads "🧪 N of M users · batch k of 4 next".
- **The batch panel.** Opening the row shows it above the device detail:
  - the progress meter;
  - who is in through another group;
  - the four parts, each with its users (first … last), devices, and state (in / next / waiting);
  - "Batch k → dry run", with the plan opening under the panel;
  - a CSV of the batches;
  - Finish, once all parts are in.
- **The toggle** turns batching off or on for a pilot. Turned off, the pilot is nested whole, as before.

## Fixes found in the browser

- **Plans hidden under the toolbar.** In 👥 the plan's heading was under the sticky region-chip toolbar. `showPlan` now scrolls the plan clear of the sticky header **and** the pane's sticky toolbar.
- **Singular nest size.** A nest step read "(1 devices)". It now reads "1 device".
