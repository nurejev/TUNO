# T01 device review and baseline editor — beta 10628

Date: 2026-09-29. T01 version: 1.0.72. Local implementation and validation; not evidence of a live deployment.

## Delivered workflow

1. **Overview:** a scan opens as read-only evidence, with device identity, collection time, observed blocked/audited/allowed counts and collection limitations. It does not create or replace a draft. Harvest modification dates are labelled as such; the guided download/open handoff checks the device and filename.
2. **Current policy & sources:** separate device snapshot, generated scan proposal, working draft and readable Intune profiles. Creating a draft is explicit; replacing a draft requires confirmation. Partially unread tenant profiles cannot be adopted as complete policies.
3. **Edit baseline:** add a rule, find/remove existing rules and undo the last change. Changes update the predictions and exports without modifying the original scan. The source and its collection time stay visible. AuditOnly is informational during the audit workflow, rather than a high-severity defect by itself.
4. **Check changes:** independent scenarios for current device policy, scan proposal, working draft and the narrower Intune export. Switching scenarios never replaces a draft. Recorded outcomes remain separate from hypothetical enforcement. Read-only scenarios cannot record draft decisions. File names take precedence over opaque binary identifiers in the event list.
5. **Pilot & deployment:** a separate step. One readiness assessment checks readable matching audit policy content, grouping receipt, evidence quality/freshness, unresolved file predictions, policy findings and explicit pilot/recovery review. Editing invalidates the audited-content check. The existing deliberate enforcement override remains available; readiness is not an absolute deployment prohibition.

## Assessment boundaries

- Predictions are a standard-user approximation from supplied metadata, not Windows AppLocker evaluation or a live merged-policy simulation. Administrator-only rules are excluded. Unknown membership, missing publisher fields or version bounds remain unknown where needed.
- Historical event outcomes can reflect older policy versions. A successful execution does not prove the new draft will allow it; an audit event is not an actual block.
- Repeated events are aggregated by path, hash, publisher/product/binary, version, user and collection. Counts represent file identities, not applications or devices.
- DLL display filtering never changes assessment totals. Collections absent from the proposed export may still exist through local policy, GPO, another Intune grouping or Managed Installer. The Intune scenario explicitly explains its omissions.
- User-profile paths no longer mean an automatically accepted block. Acceptance requires a reason and is scoped to the tenant, exact draft, device and file identity. Old path-only decisions are not reused.
- A fresh scan replaces prior separate events; a different-device event bundle is rejected. A draft can deliberately be assessed against another device, with its original source retained.
- Collection warnings and unknown evidence block normal readiness. No count or checkbox proves a representative pilot. The generated baseline is a proposal, not business approval.

**Historical scratch-suite limitations**

These are not included in the 851 tracked checks. Baseline runs were made against HEAD before comparing their results with the new workflow:

- The old scan/Intune scratch suite already failed two remediation-name checks on HEAD. It additionally assumes importing a scan creates a draft, expects the old rail/by-design grouping, and expects XML imports to discard scan evidence. Those expectations intentionally no longer apply; the tracked review suite covers the replacement contract.
- The old fix suite passed 80/80 on HEAD. With an explicit draft-creation step added in a temporary copy, 79/80 pass. The remaining assertion selects the first AuditOnly/empty-collection finding by sort order and expects the literal button text “Add default rules first”; after AuditOnly became informational it selects the separate “Add default rules” finding. Neither action offers a bare Enable. The original scratch file was not altered.
- The old script guard normalizes only `$script:TunoBuild`, not the first-line build banner introduced in 10627. Its unmodified version falsely reports 14 behavior changes for stamp-only edits. The temporary corrected guard normalizes both stamps; no script behavior version was inflated to satisfy this stale check.
