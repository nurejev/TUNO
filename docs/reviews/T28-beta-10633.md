# T28 MDE rollout — beta 10633

Date: 2026-09-29. T28 0.2. Queue item 195.

## Why

Three asks from Mihai after 10632:

1. "creator is owner"
2. "wave groups need to have device groups also". Policies with `- U -` in the name are user policies, and those with `- D -` (or `-u-`, `-d-`) are device policies. The device groups are `PVM-DG-MDE-WAVE-<region>` and the user groups `PVM-UG-MDE-WAVE-<region>`.
3. "also add a PVM-UG-MDE-Exclusion and PVM-DG-MDE-Exclusion groups to be created"
4. "also add the option to add the waves groups to right policies as a include, and add the exclude group to all the new policies. next a option to auto exclude the waves from the old policies"

## What changed

| Area | Change |
| --- | --- |
| Config | `waveRegions` + `waveDevicePrefix` + `waveUserPrefix` + `exclusionDevice` / `exclusionUser` + `exclusionDescription`. `normConfig` derives `groups` (role, audience, region, twin) and the flat `waves` name list. A 10632 config (a list of full UG names) migrates to regions. |
| Audience | `audienceOf(name)`: a one-letter `d` / `u` segment in the normalised name. Both or neither → null. `WIN-DCP` and `PVM-DG-…` are not a D. |
| Twin | When the support matrix refuses excluding a wave (user wave vs a device-targeted old policy, or the reverse), the same region's wave of the other kind is proposed, and the step says whose twin it is. A missing twin is named, with a link to 🌊. |
| Resolved | `pairReach` / `compare` take the twin map. An old policy that excludes the twin of every wave the new policy includes is resolved, flagged `byTwin`. |
| Staged | An unassigned `- D -` policy is planned with the device waves only (`wavePool`). |
| Target kind by name | When none of an old policy's include kinds can be read, its own `- D -` / `- U -` decides, and the step says so (`effectiveTargets`). |
| Include warning | Including a user group in a `- D -` policy (or the reverse) is warned in the dry run. It is still allowed. |
| Exclusion groups | Two rows under ⛔ in the 🌊 pane, created by the same path with their own description, with "exclude from the rest →" that selects the new policies of their kind. |
| Owner | `createWave` names `/me` in `owners@odata.bind`, reads `/owners` back, and falls back to `owners/$ref`. It retries the create without owners only when the refusal is about the owner. The ledger row fails when the owner could not be set. |
| Rollout actions | A card on top of the 🌊 pane, narrowed by region chips. Each action is one dry run, read fresh and composed through T11's `planFor`, with the usual backup / confirm / drift check / read-back / ledger / undo. What is left out is listed with its reason.<br>① Every existing wave into each new policy of its kind.<br>② The exclusion group of the kind each new policy is **assigned** to (support matrix). The `- D -` / `- U -` name decides only while the policy is unassigned. A `- D -` policy on user groups gets the user exclusion group, and the plan says why.<br>③ The ⚔️ proposals restricted to waves, out of the colliding old policies. A wave never leaves an old policy ahead of the new policy that replaces it. The old policies among them with a 🧹 gap are counted. |
| 🌊 pane | Rows grouped by region: device wave, then user wave, then the exclusion groups. The kind is shown only where the read disagrees with the name. |

## Microsoft Learn

- *Create group* (Graph): an admin who creates a Microsoft 365 group becomes its owner automatically, but not when the group is a security group. That is why the owner is set explicitly and then read back.
- *Assign policies in Microsoft Intune*, support matrix: excluding user groups from device-group assignments (or the reverse) is not supported. That is why the twin exists.
