## 🔎 Find their logons in Defender

It lives in 👥 → 🕳 Left out, over the list of users with no Windows device. The lookup covers the users in view: the wave, or the country chip when one is on. That is all of them, not only the 300 rows shown.

**The query** (`MdeMembers.logonKql` and `readLogons`):

- It runs through Graph's `POST /security/runHuntingQuery`, with `Timespan: P30D`, one query per 200 users.
- It reads `DeviceLogonEvents`: successful `Interactive`, `RemoteInteractive`, `CachedInteractive`, `CachedRemoteInteractive` and `Unlock` logons.
- It matches a user by their **on-premises SID** (`AccountSid`, for hybrid accounts) or their **account name**: the on-premises `sAMAccountName`, else the UPN's prefix, lower case.
- Names are escaped in the KQL string literals.
- It joins `DeviceInfo` for each device's Entra `AadDeviceId`.
- To make the match possible, the country groups' users are now read with `onPremisesSecurityIdentifier` and `onPremisesSamAccountName`. That is the same call with two more fields, so it costs no extra requests.

**What each device means** (`MdeMembers.logonsFor`):

- There is one line per device: a SID match and a name match on the same device add up. Newest first.
- The device is classified against what the 👥 read already holds:

| Kind | Said as |
| --- | --- |
| In Intune (by `azureADDeviceId`) | "in Intune — primary user X (Country), in the wave through INT-SG-D-XXX", or "not in a wave yet", or "no primary user — no wave". The device follows **that** person's country. |
| In Entra, not in Intune | "Defender only — in Entra (join type), not in Intune: no wave reaches it". The device groups follow Intune primary users. |
| Neither | "Defender only — no Entra object: it cannot be a group member" |
| No logon found | "no logon on a Defender device in 30 days — web or mobile only, or a device Defender does not see" |

**On the screen:**

- The column appears once any user in view has been looked up. It shows up to three devices per user; the CSV has them all.
- The 🕳 CSV gains a "Logged on to (Defender, 30 days)" column.
- **⧉ Copy the KQL** copies the same query for the Defender portal. Without a clipboard, it saves a `.kql` file.
- **A refusal** (401 or 403, or consent wording) says what's needed: `ThreatHunting.Read.All` with admin consent, and Security Reader or a Defender role with advanced hunting for the signed-in admin. It points at the KQL instead.

## New scope, taken in the open (R18)

`ThreatHunting.Read.All`, delegated, admin consent, is declared in three places in this commit:

- `Graph.SCOPES.hunting` in `js/graph.js`;

It is asked for only at the 🔎 click. Graph also gates it on the caller's role, so consent alone doesn't open it.
