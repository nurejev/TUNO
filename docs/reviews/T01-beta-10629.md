# T01: creation and Audit improvement — beta 10629

Date: 2026-09-29. T01 1.0.73. Local implementation; not a published beta or live-tenant validation.

## Workflow

1. **Create & deploy**: start an Audit draft, import XML or a reference scan proposal, edit rules, publish and assign through the existing deployment flow, and set up Device Scan.
2. **Analyze & improve**: select the readable, dedicated Audit profile already deployed to Intune; import scan results locally or through Harvest; compare actual execution identities to that profile; select additions or edit/remove rules; preview differences against a fresh read; update that same profile in AuditOnly; sync and rescan.

Each workspace retains its own draft, evidence, deployment state and selected policy during the browser session. Reloading does not persist these drafts. The analysis workspace does not adopt the scanner-generated baseline automatically.

Results default to differences and unknowns. Historical events already covered and files outside selected collections remain available through explicit categories. Inventory-only files are not suggestions. Predictions use the existing standard-user approximation; the original execution outcome remains separate. Intended blocks retain the existing tenant/draft/device/file-scoped decision mechanism. Editing a draft invalidates decisions scoped to its prior contents.

## Update boundaries

- Bind to an explicitly selected immutable Intune profile ID and original grouping. PATCH only omaSettings, preserving name and assignments. Preserve existing collection URIs including DLL. New DLL collection scope is refused.
- Require readable AuditOnly collections. Reject mixed profiles, multiple groupings, duplicate collections, unread values, unsupported XML extensions/attributes and missing rule IDs, rather than silently dropping unsupported content.
- Re-read before preview and before writing; reject changed tenant, draft or reference fingerprint. Send If-Match when Graph returns an ETag. Without an ETag, fresh reads reduce but cannot eliminate concurrent service-side edits.
- Explicit confirmation precedes the write. Read back and compare rules, modes and grouping. An incomplete read-back is reported as an unverified sent update. No write retries are added.
- Download the original profile before updating. Recovery requires restoring its prior rules to the same profile, followed by device sync and validation; recovery is not automated or live-tested here.
- Scan grouping/rule receipt is contextual evidence from a merged device snapshot. It does not isolate the selected profile or prove current receipt. Existing events do not become evidence for a newly updated version.
