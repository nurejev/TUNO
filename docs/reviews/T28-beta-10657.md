# T28 MDE rollout — beta 10657

Date: 2026-09-30. T28 0.24. Promotion queue item 219.

## Why

Mihai, off T15's MDE baseline table (ASR rules: 3 match, 15 conflict, 1 not configured): "for t28, make an option to adjust the settings of these policies. make it a dedicated button".

Mockup: `t28-adjust-settings-mockups.html`. He picked **B: a header button and a pane of its own**, and **ASR rule modes only** for the first build.

## What changed

**🎛 Adjust settings** — a header button (shown once the tenant is read) and a rail node under ⚔️. The pane has:

- one row per ASR rule and new-set policy carrying it: mode now, a mode picker, T15's baseline (`Defender.MDE_BASELINE.asr`), and a chip (matches / ≠ baseline / Now → New);
- filters: ASR rules, ≠ Baseline, ✎ Changed here, Not in the new set; plus the policy search;
- **Set shown to baseline** and **Clear changes**;
- a sticky bar with the pending count, Discard and ② Dry run.

**Which policies.** The new set by name: generation `new`, plus a new-prefix name that ⚙️ Leave out takes out of the comparison. The one-rule `WIN-SEC-AttackSurfaceReduction-D-NN` policies are on that list by default (10642), and they are the policies this is for. They are marked ➖ left out. Out-of-scope prefixes (AVD, WinServ) and TO-BE-REMOVED names never qualify, so the `AVD-SEC-…ASR-Rules(audit)` policy is never edited.

**What is editable.** Only a rule the policy already carries as its own per-rule child. A rule no new policy carries (Webshell) is listed and never created. A policy that uses the legacy `guid=mode` string is listed and not edited. Warn is not offered for LSASS and Office code injection (Learn: ASR rule modes).

**The write** (engine `MdeAsr`, `js/mdeasr.js`):

1. ② Dry run: each policy is read fresh (`GET` the policy + `/settings?$expand=settingDefinitions`). A rule whose mode moved since the read is left out as drifted.
2. ③ Backup: the policies and all their settings as read, as JSON.
3. Tick, ④ Apply (scope `DeviceManagementConfiguration.ReadWrite.All`, the one T28 already asks for assignments).
4. Per policy: re-read; skip as drifted if `lastModifiedDateTime` or the mode changed since the dry run; `PUT /beta/deviceManagement/configurationPolicies/{id}` with name, description, platforms, technologies, scope tags, `templateReference.templateId` and every setting as read (ids and expansions stripped), only the chosen modes changed; read the settings back and verify.
5. The run lands in 📜 (kind `settings`) with its backup; ↶ Undo plans the reverse on the 🎛 pane through the same gates.

The settings catalog only takes settings as a whole-policy PUT, which is why every other setting is re-sent exactly as read.

Also: `Graph.put`; a demo `PUT` route that keeps the settings so the read-back sees the write; ❓ How it works and the intro say settings can now be written here.
