So it is a flake, not broken code. This build does two things about it.

## 1. A failing check names itself on the run page

`tests/run.js`, only when `GITHUB_ACTIONS` is set:

- Each suite's output is piped through as before.
- For a failed suite, its `FAIL:` and `timeout:` lines (or, failing those, its first `Error` line) are printed as `::error file=<suite>,title=<file>::<line>`, up to ten, escaped per the workflow-command rules.
- They then show as annotations on the run page, which anyone can read.

Locally nothing changes: the runner still uses `stdio: "inherit"`.

## 2. The T28 screen suite waits for a read to settle

A T28 read renders the page, then keeps going (group kinds, setting names) and renders again. A check that holds an element across that second render clicks a node that is no longer in the page. On a slow runner that second render can land in the middle of a check. This is the race that fits a run which failed quicker than the passing ones.

- `MdeRolloutTool._state()` now also reports `running`, `busy` and `enriching`.
- The suite's `idle()` waits for all three to be clear after the first read and after each re-read. It replaces a fixed `sleep(50)` after the re-read.
- The tool itself doesn't change.

## Validation

- **Tracked suites: all 17 pass**, with and without `GITHUB_ACTIONS=true`. With it, a passing run prints no annotations.
- **A made-up failing suite** under `GITHUB_ACTIONS` prints `::error file=tests/x/a.test.js,title=a.test.js::FAIL: something 100%25 broke`. `%` is escaped.
