# T01 custom-profile values on beta — beta 10645

Date: 2026-09-30. T01 1.0.77.

## Evidence

- Read diagnostic (schema 2, build 10641) for the R27.1 AuditOnly profile: all four collections returned `value: "****"`, `isEncrypted: false`, no secret reference, **even after the single-profile re-read**.
- T04 export of the same AuditOnly and Enforced profiles: `isEncrypted: true` and the full `<RuleCollection …>` XML for StoreApps, EXE, MSI and Script.

## Cause

`AUTH_CONFIG.graphBase` is v1.0. `Graph.customProfiles`, the hydrate re-read, `getOmaSettingPlainTextValue` and T01's `readAuditTarget` used relative paths, so they all went to **v1.0**. The v1.0 `omaSetting` type has no `isEncrypted` and no `secretReferenceValueId`, so v1.0 can only return the masked value with no way to fetch the real one. T04 reads through `readAll(..., { beta: true })`, which is why the export had the XML. 10641 correctly caught the mask, but it was still asking the wrong endpoint.

## Change

- `js/graph.js`: `customProfiles` reads beta, paged through `readAll` (it used to read one v1.0 page with `$top=999`). New `profileUrl(id)` returns the beta single-profile URL, used by the hydrate re-read and `omaSettingPlainText`.
- `js/applocker.js`: `readAuditTarget` (the Audit-update compare, the re-read before PATCH and the read-back after it) reads through `Graph.profileUrl`.
- Unchanged: the PATCH and `createProfile` still write to v1.0, the path that was already proven. The 10641 mask handling stays as a safety net.

## Validation

- `npm test`: all 17 suites pass, **1416 assertions**. Five new audit-workflow checks (58 total).
- Supplemental: `t04-backup-tests` 160/160. One expectation there was updated because it pinned the old v1.0 re-read URL. `graph-read-tests` 245/257 and `t01-xml-tests` 38/40 give the same counts as HEAD.
- Syntax check passes. Script changes are build stamps only.
