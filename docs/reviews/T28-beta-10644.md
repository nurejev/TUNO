# T28 MDE rollout — beta 10644

Date: 2026-09-30. T28 0.12. Promotion queue item 206.

## Why

Mihai sent screenshots of T28 reading the tenant as soon as its tile was clicked: "clicking the tool should offer to read the tenant, and not start automatic."

Opening the screen called `run(true)` whenever TUNO held the sign-in read or was still reading it. That is the read, the legacy templates and the wave-group lookup, followed by group kinds and setting names. None of it was asked for.

## What changed

`onShow()` no longer reads. When nothing is read yet, it calls `offerRead()`, which fills `#mrBody` with a card:

| Situation | The card offers |
| --- | --- |
| The sign-in (or shared) read is held | **↻ Read the tenant** (fresh) and **Use the sign-in read from HH:MM** |
| The sign-in read is still running | **↻ Read the tenant** and **Wait for the sign-in read** |
| Nothing held (cold) | **↻ Read the tenant** |

- The card says what a read takes and that reading changes nothing: T28 writes only when a plan is applied.
- `data-mrread="fresh"` → `run(false)`; `data-mrread="attach"` → `run(true)`, which removes the card and keeps its progress in the same place.
- The header's **↻ Read the tenant** is unchanged (always fresh).
- Once something is read, opening the screen again keeps it, as before.
- The ⊘ header button stays hidden until a read exists. **Fixed:** it had shown all along, because `.btn{display:inline-flex}` beat the `hidden` attribute. `.mr-exbtn[hidden]{display:none}` now holds it, as `.mr-export[hidden]` already did. jsdom has no stylesheet, so the suite only checks the attribute; the browser check covers the rest.
- ❓ How it works says that opening reads nothing.

This is the empty state of the screen, not a layout change to the panes, so it went straight to code.
